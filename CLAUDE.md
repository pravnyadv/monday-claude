# monday-claude — maintainer notes

This repo is a small monday.com CLI (`mon.js`) plus a Claude Code skill. `mon.js` wraps the monday.com GraphQL API and encapsulates the gotchas below so callers don't hand-roll GraphQL. End-user setup is in `README.md`; the agent-facing usage is in `skills/monday-tasks/SKILL.md`. This file is for anyone editing the CLI.

## Shape

- Code layout: `mon.js` holds config, the GraphQL client and the commands; `lib/post.js` is the posting pipeline (mentions, CC, minify, writing-rule check); `lib/columns.js` finds columns and encodes `set` values by type; `lib/mcp.js` is the hosted-MCP client. Every write goes through `write(label, details, send)`, which is where `--dry-run` is enforced, so a new write command gets dry-run by using it. `setRuntime()` lets tests swap in a fake GraphQL client, MCP client and config.
- Session links: `lib/links.js` owns `links.db` (node:sqlite; every read and write of it goes through `openLinks`), `lib/transcripts.js` reads Claude transcripts and git checkouts, `hooks/links-hook.js` is the live hook (also in `hooks/hooks.json` for plugin installs), and `mon.js links` is the query, `links add`, `links import`. `lib/claude-settings.js` is the only code that touches `~/.claude/settings.json` (merge, never replace; `.bak` first), used by `setup`. Evidence order for an MR's task: the task link in its description (fetched with glab/gh), then pulse ids in the create command, then the task the session named last before creating it. An MR's branch: the host's source branch, else the earliest creation's checkout, never a later guess. Count a command as an MR creation only when a shell segment starts with `glab mr create`/`gh pr create` (sessions that quote the phrase in tests or greps would otherwise create false links).
- `reference.json` (gitignored, account-specific) holds board/column ids, per-board status label sets, and a people→id map. It is generated by `mon.js init <boardId>` / `mon.js refresh`, not hand-written. `reference.example.json` documents the shape. Its location: `MONDAY_CLAUDE_CONFIG` if set, else a `reference.json` next to `mon.js` (existing setups), else `$XDG_CONFIG_HOME/monday-claude/` (so a plugin update can't wipe it). See `refPath()`.
- Network calls go through `createClient({ fetch })` — retries 429/5xx/network/complexity errors with backoff (honoring `Retry-After`). The seam is injectable so command/mutation logic is unit-tested without hitting monday. `list`/`search` page via `items_page` + `next_items_page`; `fetchPeople`/`listBoards` page too.
- The token comes from the `monday_api_key` env var (name is `tokenEnvVar` in `reference.json`). It acts **as the user it belongs to** — every write is that user.
- `mon.js` normalizes two config shapes on load (a legacy role-keyed shape and the current id-keyed shape), so an older `reference.json` keeps working.
- Endpoint `https://api.monday.com/v2`; headers `Authorization: <token>` and `API-Version` (item descriptions need >= `2026-04`).

## Who posts

- An OAuth/MCP monday integration posts **as whoever authorized it**, which may not be the token owner. If posting identity matters, drive writes through `mon.js` (the `monday_api_key` token) and avoid the hosted integration for writes.

## Column detection

- `init` auto-detects the status column (type `status`/`color`) and people column (type `people`/`person`) per board, preferring an exact `status`/`people` type. When a board has several candidates it prints them all and marks its guess; the user overrides by setting `statusColumn`/`assigneeColumn` in `reference.json`. `refresh` never re-guesses a column that's already set.

## API gotchas (hard-won)

- **Item descriptions** are special docs invisible to the `docs` query and MCP `read_docs`. Read: `items { description { blocks { id type content } } }` — each block's `content` is JSON with a `deltaFormat` array (join the `insert`s for text). Write: `set_item_description_content(item_id, markdown)` — select `{ success error }` (its result type has no `id`). This REPLACES the whole doc (no append). `desc-get` / `desc-set` handle both.
- **Description images** are `image`-type blocks whose `content` JSON carries an `assetId` (NOT the item's `assets` field, which stays empty for description images). Resolve the id via the top-level `assets(ids:[ID!]!)` query (note the non-null list type) to get a signed S3 `public_url` (~1h expiry) that downloads without auth. `desc-images` does this; `desc-get` marks each image inline as `![name](assetId:<id>)`.
- **Update HTML must be compact.** monday renders every newline in an update body as an empty line, so pretty-printed HTML (`</p>\n<ul>\n<li>`) shows big gaps. `minifyHtml` drops whitespace between tags only when it spans a newline: a plain `</a> <a>` space is content, and stripping it made CC lines read "@A@B".
- **Updates / @mentions — use INLINE ANCHORS, not `mentions_list`.** The update body is **HTML, not markdown**. Embed each mention as its own anchor where you want it:
  `<a class="user_mention_editor router" data-mention-type="User" data-mention-id="<userid>">@Name</a>`
  The anchor both renders as the blue clickable name inline AND registers the ping, anywhere in the body. So `create_update(item_id, body)` with anchors is all you need. A bare `@Name` as plain text does NOT create a mention.
  - **Do NOT also pass `mentions_list`.** If you do, monday renders the anchors inline AND appends a trailing footer listing every `mentions_list` name, so people show up twice. No command sends `mentions_list` any more: `update`, `reply`, `update-edit` and `handoff` turn `@Name` into anchors in `lib/post.js`, and `comment` is an alias of `update`.
  - **cc convention:** greet the primary person inline at the top; put any additional people on their own trailing line prefixed `CC:` with each as an inline anchor, once each.
- **An update (a "post") is not the description.** A URL like `.../pulses/<itemId>/posts/<updateId>` is one update; read it via the `updates` query, not `desc-get`: `updates(ids:[<id>]){ id item_id created_at creator{name} text_body body assets{ id name public_url file_extension } }`. Update images live in `assets` (signed S3 `public_url`, ~1h expiry). `update-get` / `update-images` handle it.
- **Threaded reply vs new top-level update.** `update` posts a NEW top-level update. To reply UNDER an existing update, `create_update(item_id, parent_id:<updateId>, body)` — both ids required; look up the parent's item via `updates(ids:[<id>]){ item_id }`. `reply <updateId>` does this.
- **Editing an update in place:** `edit_update(id, body){ id updated_at }` replaces the body and keeps the id/position, but takes ONLY `id` + `body` — passing `mentions_list` errors, and `@` text isn't a real mention. Body-only change → edit; adding/changing @mentions → delete + repost via `create_update`.
- **Subitems can't be reordered** via API (`change_item_position` → "not supported"). Display order = creation order; to reorder you must recreate (fetch desc/cols → `create_subitem` → set description → `delete_item` old).
- `create_subitem(parent_item_id, item_name, column_values)` — `column_values` is a JSON string; people `{"personsAndTeams":[{"id":<uid>,"kind":"person"}]}`, status `{"label":"..."}`.
- Deleting an update requires being its author or an admin.
- **Time Tracking** columns (`DurationColumn`) canNOT be set via `change_multiple_column_values` — API returns `InvalidColumnTypeException`. Sessions must be added in the UI. (A `numbers` time-*estimate* column is writable.)
- **Activity logs:** `boards(ids){ activity_logs(item_ids:[..], from:<ISO8601>, limit){ event user_id created_at data } }`. `created_at` is in 100-nanosecond units (divide by 1e4 for ms). `data` is a JSON string; column changes carry `textual_value`/`previous_textual_value` only for some types; numbers come as `value.value`, dates as `value.date`, status as `value.label.text`, people as `value.personsAndTeams`. Group moves are `move_pulse_from_group` with `source_group`/`dest_group`.
- **Items assigned to someone:** `items_page(query_params:{rules:[{column_id:"<people col>", compare_value:["person-<userId>"], operator:any_of}]})`.
- **Board-wide updates** (for unanswered mentions): `boards(ids){ updates(limit:100, page:N){ id item_id created_at creator_id body replies{ id creator_id created_at body } } }`, newest first.
- **Time tracking can be READ** through the public API: `column_values(ids:[col]){ ... on TimeTrackingValue { duration running history { id started_at ended_at started_user_id status } } }`. The history ids are the same ids the browser's internal endpoint uses. Writing is still impossible (the docs' "Create: Yes" means creating the column).

## The hosted MCP server (tested 2026-10-16)

- `https://mcp.monday.com/mcp` accepts the personal API token as `Authorization: Bearer <token>`, so every tool acts as the token owner (proved with `me` and with a create/update/reply/edit/delete round trip on a throwaway item). OAuth clients act as whoever authorized them instead.
- About 100 tools. JSON-RPC over HTTP: `initialize`, then reuse the `mcp-session-id` response header. Responses are JSON or SSE (`data: {...}` lines). Tool failures come back either as `isError` or as a text result starting `Error:`; some argument problems come back as plain text with no error flag ("Input must contain ...").
- It is not a stable API: tools have been renamed within days of release, there is no version to pin, and argument types disagree (`boardId` is a number for most tools and a string for the automation tools). `get_automation_statistics` fails on boards whose id doesn't fit a 32-bit int. That is why GraphQL stays the backbone and the MCP is used only where GraphQL has no equivalent (meetings, `board_insights`, automations).
- `create_update`'s `mentionsList` appends a mention list after the body: the same duplicate-footer problem as `mentions_list`. Inline anchors in the body work through the MCP too. Newlines between tags are stored as `<br>`, so compact first.
- `all_api_read` refuses mutations ("only accepts read queries"). `submit_bug_or_feature_request` is annotated read-only but sends feedback to monday, so the passthrough blocks it.
